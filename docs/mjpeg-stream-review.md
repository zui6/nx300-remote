# MJPEG 推流代码审查（离线，未上机）

> 2026-11-22 13:10
> 对象：`daemon-build/api_server.c` 里新增的 `/api/v1/liveview/stream` 实现
> 结论：**有 2 个 P0 级问题，其中内存放大型足以解释相机重启**

---

## P0-1：内存放大（最可能是重启主因）

三处叠加，且都乘以并发数：

| 来源 | 单连接占用 | 代码位置 |
|---|---|---|
| `SO_SNDBUF` 设为 512 KB | 512 KB 内核缓冲 | `MG_EV_ACCEPT`（**历史代码**，原本无害）|
| `send_mbuf` 上限 256 KB | 256 KB 用户态缓冲 | `stream_poll` 的守卫 |
| 单帧 JPEG | ~5–50 KB | 每帧临时 |

`MAX_STREAMS = 4`，最坏情况：

```
4 × (512KB + 256KB) ≈ 3 MB
```

**相机空闲内存只有 5–9 MB。** 一旦客户端卡住（我测试时的 Python 超时就是），
数据堆在里面不释放 → OOM → 看门狗重启。

> 这是我的直接责任：历史代码里 512KB 的 sndbuf 是为"一次发完一帧 JPEG"设的，
> 我把它和"长时间堆数据"的推流放在一起，没重新算账。

## P0-2：N 个客户端 = N 倍编码

`stream_poll` 是**按连接**调用的，每个连接都会独立跑一次
`liveview_encode_jpeg()`：

```
4 个客户端 × 25 fps = 100 次/秒的 JPEG 编码
```

266×160 一次约 5 ms → **白烧 50% 单核**，还带来持续的 malloc/free 抖动。

正确做法是**每个 tick 只编码一次**，然后广播给所有参数相同的客户端。

## P1-1：死连接不会及时释放

WiFi 掉线时 TCP 半开，mongoose 可能几分钟都收不到 RST。期间：
- 我们继续按 fps 编码
- 数据继续堆进 send_mbuf（虽有 256KB 上限，但到达上限后仍每 tick 尝试编码）

**没有空闲超时**，一个"幽灵客户端"能长期占着 CPU 和内存。

## P1-2：没有全局帧率上限

`fps` 只校验了 1–60。单个客户端就能把编码压到 60fps。

## P2：其他

- 发了 `Connection: close` 但没有设 `MG_F_SEND_AND_CLOSE`，语义不一致
- `jpeg_nv12_encode` 返回的是**内部静态缓冲**，多客户端时靠"立刻发送"才能保证正确
- 连接被复用于新请求时（keep-alive），会往流里再塞一个 HTTP 响应头

---

## 修复方案（已改到源码，未部署）

| 项 | 改法 |
|---|---|
| 内核缓冲 | `SO_SNDBUF` 从 512 KB 降到 **64 KB** |
| 用户态缓冲 | `send_mbuf` 上限从 256 KB 降到 **64 KB** |
| 并发 | `MAX_STREAMS` 从 4 降到 **1** |
| 编码次数 | 每个 poll tick **只编码一次**，广播给所有流 |
| 死连接 | 记录最后一次成功发送时间，**10 秒没有进展就断开** |
| 帧率 | 全局钳制到 **30 fps** |

修复后的最坏内存占用：

```
1 × (64KB + 64KB + 50KB) ≈ 180 KB
```

比之前小了一个数量级。

## 上机前必须满足的条件

1. 用**独立端口**起实验实例（例如 8081），不替换稳定 daemon
2. 客户端必须是**自己写的、会正常读取**的（不能用会超时的临时脚本）
3. 跑之前确认 `MemFree > 12 MB`
4. 全程有人看着，随时能拔电
5. 同时只允许 1 个观看端

## 教训

这台相机（单核、500 MB、空闲 5–9 MB）**没有任何余量**接受"缓冲换平滑"的常规做法。
以后任何要在相机上跑的东西，必须先把**最坏情况内存**算出来，并留 5 倍余量。
